# CLAUDE.md - Maze City

A Roblox tower-climbing maze game, built entirely from this repo via Rojo. There is no Studio plugin and no hand-placed geometry. The world generates server-side at startup and extends itself lazily as players progress.

Players enter a building at street level, solve a maze on each of 10 floors against a per-floor timer, climb spiral stairwells to the roof, and ride a slide from designated exit buildings to the next section of the city. Every roof, exit building or not, also has a zipline down to the plaza outside its own door, so topping out is never a dead end. Higher floors have walls that slowly move. Enemy types vary by building style and can be overridden per section.

## Core architectural rules

**1. Generation produces geometry and tags. Runtime services read tags. Nothing else crosses that line.**

- `MazeGenerator` (ModuleScript) creates parts, sets attributes, applies CollectionService tags. Zero gameplay logic.
- `WorldBootstrap` is the only caller of `MazeGenerator`. It builds `Config.World.PregenerateSections` sections at startup, then lazily builds section N+1 when anyone touches a `SlideEntrance` targeting it.
- All gameplay (timers, moving walls, enemies, slides, bounce pads) lives in services that discover tagged instances via `CollectionService:GetTagged()` plus `GetInstanceAddedSignal`. This is why lazy generation works with no extra wiring: sections built mid-game are picked up by every service automatically.
- If a feature needs new data from generation, add an attribute to a tagged part. Never parent a script inside generated folders.

**2. Determinism is load-bearing.** All randomness flows from `Random.new(seed)` objects threaded through the generator. Never call `math.random` in `MazeGenerator`. Same `Config.World.Seed` produces an identical city across server restarts, and section N's slide targets section N+1's computed origin before that section exists.

Rojo infers class from suffix: `.server.lua` is a Script, `.client.lua` is a LocalScript, plain `.lua` is a ModuleScript. Keep that convention for new files.

`default.project.json` maps the three `src/` folders wholesale rather than naming files one by one, so a new file ships by being in the right folder. It used to enumerate every script, and `PickupService` was written without being added: coins generated, nothing consumed the tag, and the symptom was a player running straight through them. A service that appears to do nothing is worth checking against the built place (`rojo build -o /tmp/check.rbxlx`) before it is debugged as a logic bug.

## Toolchain and workflow

Install tools once: `rokit install`. Rokit reads the existing `aftman.toml` manifest, so no migration is needed. Aftman itself is archived upstream and its Homebrew formula was disabled in July 2026; do not try to install it.

```
rojo serve                    # live sync; connect from the Rojo plugin in Studio, then hit Play
rojo build -o MazeCity.rbxlx  # or produce a place file cold and open it
selene src/                   # lint
stylua src/                   # format
```

The pinned rojo must match the Rojo Studio plugin's major line. Rojo changed its API encoding after 7.4, so a 7.7 plugin against a 7.4 server fails at connect with `attempt to index number with 'protocolVersion'`. If Studio shows that, bump the pin rather than downgrading the plugin. `rojo serve` also defaults to port 34872, so a server for another project on that port will quietly serve the wrong tree; `curl -s localhost:34872/api/rojo` names the project actually being served.

Studio's role is reduced to being the runner: press Play, the server builds the city, test, stop. In edit mode the workspace is empty except whatever Rojo syncs. Do not save generated geometry into the place file; it is a build artifact. If a play session leaves anything behind, delete `workspace.MazeCity`, `workspace.LiveEnemies`, `workspace.LivePets`, `workspace.EnemyEffects` and `ServerStorage.GeneratedEnemyModels`. The last of those is the one enemy rig template per type that `ModelGenerator` builds at startup; it rebuilds itself from scratch every run, so a stale copy is clutter rather than a bug.

The one thing Studio is still needed for is content that is genuinely art. Rigs go in `ServerStorage/<Kind>/<Name>`: enemies at `ServerStorage/Enemies/<TypeName>` matching keys in `Config.EnemyProfiles`, pets at `ServerStorage/Pets/<model>` matching the `model` field of a `PetCatalog` entry or one of its evolution stages. Until they exist both services build a rig procedurally from that row's `look` recipe, so the game is fully playable from a cold `rojo build` with zero Studio-side setup and an artist's model wins by name whenever one arrives.

## Startup sequence

1. `WorldBootstrap` requires `MazeGenerator`, creates `workspace.MazeCity`, builds sections 1..PregenerateSections. The generator yields (`task.wait()`) between buildings so startup does not freeze the server.
2. `workspace:SetAttribute("MazeCityReady", true)` when pregeneration finishes.
3. If `Config.World.LazyGeneration`, bootstrap binds every `SlideEntrance` (current and future) and builds the target section on first touch. Ride time down the slide covers generation time; `ensureSection` also blocks duplicate concurrent builds.
4. Services bound tags at their own startup and via added-signals, in any order relative to generation. Order independence is a requirement, not an accident: never write a service that assumes geometry exists at require time.

## Generation invariants (do not break these)

These encode fixes for real bugs in an earlier version. Any change to `MazeGenerator` must preserve them.

1. **One slab per level boundary.** Level N's floor is the only horizontal slab at `Y = N * LEVEL_HEIGHT`. No separate ceiling for level N-1. The hole in level N's floor is positioned by level N-1's stair location, so the top step lands flush with the floor above. The old version had a ceiling and floor at the same Y with holes in different corners, making towers unclimbable.

2. **Stair cells are reserved before carving.** Each level picks an exit cell plus the cell inward of it, passes both as `reserved` to `newGrid`, carves around them, then seals both and cuts exactly two openings: bottom stair cell to the maze, bottom to top stair cell. Never open or close walls of an already-carved maze elsewhere; the maze is a spanning tree and post-hoc edits orphan regions.

3. **Perpendicular spiral, and the exit is half a floor from the entry.** `exitSide = rotateSide(entrySide, +/-1)`, never 0 or 2. The exit cell of level N is the entry cell of level N+1. This keeps stair holes and arrival triggers aligned across floors. Perpendicular alone still allowed the two to sit a cell or two apart near the corner the sides share, which is a floor climbed without entering its maze, so `pickExitIndex` draws only from the edge cells at least `STAIR_MIN_SEPARATION_FRAC` of the footprint from the arrival, in a straight line because nothing is carved yet. It is one draw either way, so the stream length per level is unchanged; the values are not, and changing the fraction reshuffles the city.

4. **Sections are self-contained except slide targets.** A section references section N+1 only through `MazeGenerator.sectionOrigin(N + 1)`, which is pure math. Changing plot layout constants changes every slide target, which is fine as long as it changes them consistently; never hardcode a world position.

5. **Tags carry Section, Building, Level attributes.** Runtime services key everything off these three. Any new tagged part type must set them. `SlideEntrance` additionally carries `FromSection`/`ToSection`, which lazy generation depends on, and `ShopItem` carries `Upgrade`, the key into `Config.Shop.Upgrades` that SaveService resolves a purchase against. That one attribute covers both kinds of pedestal, passive and ability alike, and deliberately: whether a row is an ability is a property of the row (`Mode`), not of the plinth, so adding abilities to the stall added no attribute and no tag. `EggPedestal` carries nothing extra: every roost in the city is the same roost, and which one an egg was placed at is not a thing the incubator stores. `RoofTrigger` carries `ArrivalX/Y/Z` because its centre is not where the stairs come up, and `LevelTrigger` carries `Route`, the walk from that floor's arrival cell to its stairwell, as `;`-separated integer offsets from the trigger's own position. Offsets rather than world points so a client can rebuild them without knowing `CELL` or the plot origin; the longest across three sections is 79 hops and 624 characters.

6. **Geometry added after a baseline draws no random numbers.** `buildZipline` is a pure function of `entrySide`/`entryCell`, which the maze has already fixed, so adding it left every pre-existing part exactly where it was and the delta was countable: four instances per building. Drawing from the threaded `rng` instead would have shifted every subsequent draw and reshuffled the whole city for a feature that needs no randomness. Anything landing outside a deliberate world reshuffle has the same obligation: read what generation already decided, or draw from a derived sub-stream seeded off the per-building seed, but never from `rng` itself. `buildEggRoost` is the third of these and the cheapest to check: a pure function of the footprint, so the delta is five instances per building, thirty per section, and every pre-existing part is where it was.

   `markMovingWall` is the fourth and shows the shape of it under a function that *does* draw. `tagMovingWalls` rolls a mode and four timings per wall; the mark is created after all of them, from the wall's own size and position and the mode already chosen, so it adds no draw and the stream is the one it always was. It also reads the floor off the wall (`Position.Y - WALL_HEIGHT / 2`) rather than recomputing `baseY`, which is why it is right on level 0 where the slab is lifted.

7. **Containment is a property of which function built the part.** Two collision groups are assigned at generation time and each answers one question by construction, so there is no runtime check to forget.

   `MazeWall` is what the Wall Walker may phase through. `buildWalls` puts every wall it makes into it through the single `wallPart` funnel; `buildFacade`, `buildSlab`, `buildStairs` and `buildRoof` leave theirs at Default. That is the whole of what stops the upgrade stranding anyone: a phasing player crosses any wall on a floor, lands in the apron ring between the maze edge and the facade with slab under their feet, and stops there, because the facade is not in the group. Anything wall-like must go through `wallPart` or decide deliberately not to, and anything that is a new *boundary* must not go in the group.

   `EnemyBlock` is solid to enemies and absent to everyone else, and it exists because **collision groups do not reach the navmesh**: pathfinding reads `CanCollide` and nothing else, so the only way to stop a planner routing an enemy somewhere is to put a collidable obstacle there. Two things are in it. A phantom wall, which was `CanCollide = false` and therefore a doorway every enemy in the city had always been walking through, is collidable again and passable to a character by group. And `buildStairs` stands a `StairBlock` panel in the one opening cut between the maze and the stair cell, which is what keeps an enemy on its own floor: the floor band that notices afterwards and teleports it home is a backstop, not the mechanism. An enemy still sees into a stairwell and cannot follow.

   The rules are split the way the groups are owned. MazeGenerator registers both and sets what `EnemyBlock` *means* (nothing collides with it); `Abilities/WallWalker` excuses a phasing player from both; EnemyFactory states the single pair that does collide. A new group needs the same three-way split or it will be one default nobody wrote down.

8. **A collectible is placed by generation; what it is worth is not.** A powerup orb carries no `Kind`: PickupService rolls one from `Config.Collectibles.PowerupRoll` when the orb is touched, so the same orb is a different prize to the next player and after it respawns. Generation places it and stops. This is why the roll list can gain and lose entries freely, where the old generation-time draw made its length load-bearing; it is also why removing that draw shifted the orb cells once, on levels 2/5/8, and touched no coin, the coins being drawn earlier in the same sub-stream.

9. **A collectible count is a function of the settings, not of the seed.** `buildCollectibles` places dead-end coins first, then main-path coins, then tops up from anywhere still open, so every level places exactly `DeadEndCoinsPerLevel + PathCoinsPerLevel` however few leaves its spanning tree happened to grow. Powerup orbs run through the same two pools after the coins have taken theirs and top up the same way, so every level places exactly `PowerupsPerLevel` of them; it is a count, never a per-level roll. Without both of those the part count stops being checkable: a section could differ from its neighbour for no reason anyone could confirm was the intended one. The sub-stream is `Random.new(buildingSeed + level * 31)`, which cannot collide because building seeds are at least 7919 apart.

| EnemyService | `EnemySpawn` | Bootstrap, registry and the spawn scan, and nothing an enemy does: that is the `Enemy/` module tree below. What a marker holds is `SpawnDirector.typeFor`'s answer, and nil is a real one: the markers sharing a floor share a budget, and the roll can leave a position empty. Two placement rules run inside the spend loop, after the caps so their raycasts only fire for markers about to spawn: nothing materialises within `MinSpawnDistance` of a player or in one's direct line of sight, both postponements rather than refusals. **A marker is permanent, its rig is not:** a rig is built when somebody comes within `Config.Enemies.SpawnRange` and destroyed past `DespawnRange`, measured from the rig so a chase is never deleted mid-stride. | TraversalService | `SlideEntrance`, `SlideBooster`, `SlideExit`, `BouncePad`, `ZipEntrance`, `ZipExit` | PlatformStand during rides, velocity boosters, safety release after SlideMaxSeconds. The zipline is the exception to "rides are physics": it anchors the rider and tweens them down the cable, because the descent is 195 studs and a rider who clips off a physics line lands wherever the simulation drops them. Every exit path, including the failures, goes through `endRide`, which is the only thing that unanchors. The rider hangs `ZipHangOffset` under the cable and stays upright; putting the root part on the cable and aiming it down the slope ran the line through the character lengthwise. Bounce pads are the one thing here that is not a ride: the player keeps control throughout, so a pad cannot use PlatformStand and has to fight the humanoid state machine twice over, once for the ground controller and once for the jump impulse the Jumping state applies a step later. A pad returns `BouncePadMomentumGain` of the speed it was landed on with, capped at `BouncePadMaxPower`, so bouncing in place climbs by itself. |
| PickupService | `Coin`, `Powerup` | Server owns the count in `leaderstats.Coins`; a taken pickup is hidden with `Transparency`/`CanTouch` and comes back on a timer, never destroyed. Collected two ways: `Touched` for the zero-latency path, and a `PickupRadius` sweep per living player because a 3.4-stud disc reached by touch alone had to be walked into almost exactly. The sweep is one `GetPartBoundsInRadius` per player answered by the engine broadphase, not a distance test against the 1,068 collectibles per section; both paths funnel into the same handler and guard on the same taken table, neither yielding between reading that guard and setting it. The Coin Magnet is a **second** query rather than a wider first one, coins only, at the absolute `MagnetRange` the shop sells: it deliberately tests no line of sight, so it pulls through walls, and it is capped to `MagnetHeight` of vertical reach so a top tier does not lift coins off the floor above through the slab. Widening the one radius, which is what the old `MagnetBonus` did, also vacuumed powerup orbs out of rooms the player never entered, and an orb that arrives with no orb to see reads as a bug. Nothing here draws the flight: the coin payload names the part and TimerGui clones it. The kind is rolled here, on touch, from `PowerupRoll`, not read off the orb; runtime randomness, deliberately not seeded off the world seed. Effects are restore closures, one active per player. Ghost sets `Unseen` on the character and Freeze sets `EnemyFreezeUntil` on `workspace`, both read by EnemyService; `Unseen` is this service's alone, the Cloak ability having its own `Cloaked` flag beside it so that neither can clear the other's out from under it; Reveal is drawn entirely by the client and has no server effect at all; CoinBoost pays a lump sum that is never taken back, so it is not in the undo list, plus a `coinBonus` multiplier that is. Speed is a `WalkSpeedResolver` factor named `Powerup`, so its undo removes a term rather than restoring a remembered number. Gear reaches both halves as an addend and never as a second writer: `PetMagnetBonus` widens the magnet's second query, and `PetCoinBonus` is added to the powerup's multiplier rather than chained onto it, so a 2x orb under a +25% crown pays 2.25. That is also why the coin payout carries its own fraction between pickups: `CoinValue` is 1 into an IntValue, so rounding each coin on its own would make +20% either nothing or double. Fires the `PickupUpdate` RemoteEvent, which carries only events (the ding, which powerup started); the number itself rides replicated leaderstats, so a late client reads it correctly. |
| PurchaseService | none | The Robux half of every storefront (docs/ROBUX_PLAN.md). Grants route through `PetInventory` and `data.upgrades` exactly as the coin paths do; a receipt is idempotent by `PurchaseId` in the profile's `receipts` table, recorded inside the same grant so the two persist or vanish together, and `PurchaseGranted` is returned only after `Profiles.save` reached the DataStore. An unloaded profile refuses every purchase. A receipt that can never be granted as bought (an upgrade tier not exactly the next one) pays the row's coin price instead; a full shelf is `NotProcessedYet` and the prompt gate refuses to open on full, so that path is the rare one. Upgrade grants fire `UpgradesChanged`, pet-side grants fire `PetsChanged`; `PurchaseUpdate` is its remote. In Studio it stamps synthetic product ids onto unset rows and registers `/buy`, so the whole spine runs before any dashboard product exists. |
| SaveService | `ShopItem`, `TowerStart` | The shop and the furthest-section credit; the profile it reads lives in `PlayerProfiles`. | DailyRewardService | none | One claim per UTC day off `math.floor(os.time() / 86400)`, a streak that grows while the days are consecutive, and on day seven both the streak egg and `Config.Accessories.StreakGearId`, which is the only way to own a Legendary piece of gear and the second source that keeps the loop alive once the shop is cleared. The egg pays at `>= DailyStreakLength` and the gear on `== StreakGearDay`, deliberately: the first must still pay somebody whose earned streak now exceeds a lowered length, the second is one day of the week. No world object: a daily reward that needs a walk to a kiosk is a daily reward people miss. |
| PetAnimator (client) | none | The joints of every follower in `workspace.LivePets`, posed once a frame on each machine over `PetRigDriver`. Position is the server's, because everyone sees the same pet in the same maze; pose is not, and a wing angle nobody can act on has no business being computed once and replicated N times, so the server pays nothing for motion. It writes `Motor6D.Transform`, which is local to the client that writes it and which the server writes on nothing, so the two cannot disagree. `sterilise` is what makes the joints live: a pet part is anchored unless a joint holds it, so the root anchors, the skin hangs off it, and the rig is one anchored assembly `PivotTo` carries and the joints pose. Culled to `Config.Pets.AnimateRange` off the camera. The one thing the driver refuses to know is what an ability is doing, so this reads the rig's replicated `WardRadius` and rebuilds the recharge from the pet's own catalogue row rather than anything new crossing the wire. |
| PetGui (client) | `EggPedestal` | The whole surface of the pet system: inventory, egg shelf, gear bag and gear shop, daily claim, hatch reveal, rarity broadcast. Draws the projection and, for the two storefronts, the catalogues: a shop has to name what nobody owns, so `EggCatalog` and `AccessoryCatalog` are read for a price and a name and for nothing that resolves an effect. Every other number arrives already resolved, so the client has no opinion to disagree with. Buttons fire intents and wait to be told what happened, including when the answer is no, which is what the `REASONS` table exists for. Reads the tag for two things only: whether the Place button is live, and where to draw the incubating egg, which goes in an `EggHint` model beside `MazeCity` and never inside it. Every pet row and the hatch reveal draw a real portrait of the pet, built locally from `PetModelGenerator` through `PortraitGenerator.of`: the projection already carried `petId` and `stage`, so the picture costs the server nothing and the rarity colour keeps the chrome around it. Rows do not spin and the reveal does, a spin being a RenderStepped connection per viewport. |
| TimerGui (client) | `LevelTrigger`, `RoofTrigger`, `PhantomWall`, `Coin` | The tag consumer that predates the pet UI. HUD and celebrations come off the `TimerUpdate` payload; the tags are read for the compass arrow's target, the phantom pass-through sparkle, spinning the coins within `SpinRange`, and the route trail, which decodes the current floor's `LevelTrigger.Route` into markers under one `Highlight` at `AlwaysOnTop`. Two unrelated things light that trail, the Reveal orb and the Trailblazer ability, so it owns a deadline rather than belonging to whichever drew it: both extend `revealUntil` and neither tears it down, because a cast taken during an orb used to go out with the orb. Pet gear is the third and has no clock at all, so it is a second layer rather than a third caller: `PetRouteVision` hops are drawn permanently in amber, a temporary draw takes that layer down, and clearing one puts it back, which is why the two are exclusive and there is never more than one `RouteHint`. `PetPhantomSense` is the other geared draw, one broadphase query per tick marking phantoms on the player's own storey in a `PhantomHint` model, floor-filtered because a 30 stud reach against a 19.5 stud storey otherwise marks a shortcut one floor down. Hints, never authority: a section that has not replicated yet just means no arrow for a moment. Markers go in a `RouteHint` model parented to `workspace`, never into `MazeCity`, and are cleared when the deadline passes, on a floor change, and on respawn. The coin spin is a local CFrame on an anchored part the server never moves again, so it stays on the machine that drew it. The Coin Magnet's flight is the same bargain: the pickup payload names the coin, this draws a clone of it flying home into a `CoinFlight` folder beside `RouteHint`, and the original never moves. The ding rings on the landing rather than on the pull, so a corridor taken in one sweep still lands as a rising run. |

Effects (sounds, particles, the compass billboard) attach at runtime to characters, enemy rigs in `workspace.LiveEnemies`, pet rigs in `workspace.LivePets`, or the PlayerGui. Anything an enemy leaves standing in the world rather than on itself, which since E4 is bolts, snares, arrival marks, burrow mounds and shockwave rings, goes in `workspace.EnemyEffects` and is destroyed by `EnemyCombat.clearRuntime`, which `EnemyController:stop` calls for every enemy whether or not its behavior asked. Nothing is ever parented into `workspace.MazeCity`, which stays exactly as the generator built it.

## Server modules

ModuleScripts in `src/server` hold state and rules that more than one Script needs. A `.server.lua` Script cannot be required, so anything shared has to be one of these. The two module trees, `Enemy/` and `Abilities/`, each have their own section below.

- **`PlayerProfiles`** is the saved profile and the only caller of `DataStoreService`. Its failure posture is load-bearing and predates the pet system: a profile that fails to load sets `loaded = false` and is then never saved over, so a Studio session without API access plays identically and wipes nothing. Any field added has to keep that, which is why `adopt` merges field by field against defaults rather than replacing the table: an absent field loads as its default, and that is the whole migration story for an additive change. Coins are deliberately not in it, being `leaderstats.Coins`, read back off the IntValue at save time so the number the game already replicates is the only copy. The schema is versioned twice and they do different jobs: `Config.Persistence.KeyPrefix` is the wipe, `schemaVersion` in the payload is the record. `Profiles.onReady(fn)` is how a service is told a profile is readable, and it replays for players already loaded, so registration order does not matter.
- **`WalkSpeedResolver`** is the only writer of `humanoid.WalkSpeed`. Five things want to change how fast a player moves and they arrive in any order: Fast Feet, the Speed powerup, the Wall Walker's squeeze, Sprint, and the slow a Spitter's bolt or a Trapper's snare puts on you. Each used to multiply `BaseWalkSpeed` itself and restore by writing `BaseWalkSpeed` back, which is last-writer-wins dressed up as a convention: a Speed orb taken before a phase was silently cancelled when that phase ended, and a phase started during an orb dropped the orb's 1.45 on the floor. So a source names itself and states a multiplier, and this module owns the product. Clearing `Sprint` cannot disturb `Powerup`, because clearing removes a factor rather than restoring a remembered number, and that is the whole of why the five compose. The enemy slow is the one that arrived from outside the player systems, and it is the reason `StatusDefinitions` has no `Slow` row: E2 wrote one that recorded and restored WalkSpeed itself, this module landed after it, and a status doing its own record-and-restore beside the resolver is the bug the resolver exists to end. `BaseWalkSpeed` is unchanged: still a character attribute, still stamped only by SaveService, and now the baseline the product multiplies. The factor table is keyed weakly by character, so a respawn drops every factor with the body it was applied to. The one rule for a new caller: never read `humanoid.WalkSpeed` back as a base, which is what the old call sites did and what made a boost squarable.
- **`PetInventory`** is the pet rules as functions over that table: caps, levels, evolution stages, the hatch roll, the equip list, the client projection. No remotes, no instances, no yielding. It exists because three services mutate the same inventory and three copies of a cap check is three chances for them to disagree. Every mutating function returns `ok, reasonOrValue`; a refusal is an ordinary return, never an error and never a silent no-op, because the client is going to be told why.

## Enemy AI

`src/server/Enemy/` is the AI; `EnemyService` is only the loop that decides which markers hold a rig. Content is `ReplicatedStorage.EnemyDefinitions` (one row per type), the vocabulary is `EnemyTypes`, the rigs are `ModelGenerator`, and everything that governs the system as a whole is `Config.Enemies`.

**The controller knows how to move, look, attack and die; the behavior knows when.** `EnemyController` is one per rig and is the only thing that touches the Humanoid, so the freeze deadline, the stun, the floor band and the attack tell are written once and cannot be forgotten by a module that only meant to change how something walks. A behavior is a table of hooks over `BaseBehavior`, not a subclass of the controller.

The tick order is a contract: freeze, stun, off-floor, `update`, target selection wrapped in `filterTarget` and the two transition hooks, growl, then `onChase` or search or return or `onIdle`. Three hooks can claim a tick and end it there. `onStopped` is outside the tick and runs from the controller's `stop`, which covers despawn as well as death: walking away is how nearly every enemy in this city ends. `BaseBehavior.extend` errors at require time on a key that is not a hook, because `onStateEnter` for `onStateEntered` is otherwise invisible: the module looks written, the hook never fires, and the enemy just stands there.

**Teardown is the controller's, not the behavior's.** `stop` runs `onStopped`, then calls `EnemyCombat.clearRuntime` itself, disconnects, silences the growl and destroys the plan. It was four behaviors each remembering that one call until E6's cleanup audit, which is four chances for a fifth to be written without it; the Burrower is the only type with an `onStopped` left, because unanchoring a root it anchored to travel under the floor is a thing no other module could know about. The same audit put the default `onDied` in `EnemySpawner`: that module is what puts a controller in the registry, so it owes the registry a way out, and a rig that died with nobody listening used to stay registered with a corpse standing in the maze holding a slot against `GlobalCap`.

Three things carried over from the old single-file service and must survive any change. Nothing blocks on `MoveToFinished`, whose eight second internal timeout turns a clipped corner into an enemy standing still; `EnemyPathfinding` decides arrival itself. A plan goes stale on both a timer and a drift, because the timer catches a moving wall closing across a clear path and the drift catches the player rounding a corner, and neither alone caught both. And leash is measured from the spawn marker, never from the enemy, so an enemy owns a patch of maze and can be left behind. Enemies also share a collision group that does not collide with itself, because three of them meeting in a corridor was most of "they just stand there".

No behavior in a tick parks its own thread, and that half is load-bearing: the Charger's windup used to be a `task.wait` inside the loop, and a parked thread meant a Freeze powerup landing during a windup did not stop the charge until after it had already started. Every timed move in the roster is a deadline on a state now and a new one must be written the same way. E6 corrected the stronger claim that used to stand here: a tick does yield, in exactly one place, `ComputeAsync` inside a replan. That is bounded by `PathReplanSeconds` per rig and touches no behavior's timing, but it does rule out driving every controller from one shared slice loop, which would stall on whichever rig was replanning. The thread per rig stays until pathfinding can be asked asynchronously.

**The measured cost, from E6's headless audit at the brief's 25 active enemies:** one simulated second of every rig chasing is 200 raycasts (exactly one line-of-sight test per enemy per tick, at `ThinkInterval` and not per frame) and zero path computes while the player is in sight, since a straight line skips the planner entirely; out of sight it is 75 computes, well under one per enemy-tick. The animation sweep is the only thing that runs every frame and it costs the engine nothing: no ray, no plan, just joint CFrames.

**Adding an enemy is one definitions row, a behavior (pick an existing one or add a module under `Behaviors/`), and a `look` recipe.** No service is edited. A row naming a behavior with no module gets `BaseBehavior` and one warning, so it chases and hits like a baseline Drifter with that row's numbers rather than standing there. All nineteen types have a module, a silhouette, and since E5 a way to be met: the director rolls them into floors as the roles unlock up the tower.

**`SpawnDirector` decides what a floor holds; an `EnemySpawn` marker is only a position.** The markers sharing (Section, Building, Level) share `Config.Enemies.FloorBudget`, and one roll spends it: the building's style type is the anchor, always eligible and weighted up, and every other spawnable row joins the roster at the floor its role's `Config.Enemies.Director.RoleMinLevel` gate names, so early floors feel like the building and the strange ones are met on the climb. At most one enemy per floor is disruptive or elite, a Support type needs a Basic one beside it, and Elites are capped per building across its floors, which is the Warden's rarity. `Config.SectionEnemyOverride` survives as a hard filter that waives every rule but the budget, plus the guarantee that a non-empty roster never rolls an empty floor. An assignment is per visit: rolled on first need, held through a death so the respawn brings back what the budget paid for, dropped when the last rig walk-away despawns. Director randomness is runtime randomness, never the world seed, same as `PowerupRoll`.

**`EnemySafeZones` makes the plaza pad outside each tower door somewhere enemies do not go**, as runtime boxes over the `TowerStart` parts, no new tag and no new geometry. Two questions with different callers: `covers` is the zone itself and is the player's protection (not targetable, and every landing in `EnemyCombat` refuses a victim inside one, projectiles dying at the line), `repels` is the zone plus `SafeZoneMargin` and is the enemy's exclusion (the controller turns a repelled position into the ward's walk-home branch so nothing camps the border, `isClearBetween` and `groundBelow` reject arrivals, the scan refuses spawns). Bounded in Y to the pad's own storey, because ten floors of maze stand directly above the door.

**`EnemyDebug` and the bestiary are the E5 debug surfaces and neither exists for a player.** EnemyDebug returns immediately outside Studio; inside it, chat `/enemy ...` or invoke the `EnemyDebugCommand` BindableFunction for spawns, waves rolled through the director, clear, the only damage path in the game, an AI freeze, and ring/path/label visualizers drawn into `workspace.EnemyDebug`. `PortraitGenerator` frames any client-built rig in a ViewportFrame (`of`), with `portrait` the enemy convenience over the shared `ModelGenerator`, so the client draws its own portraits and the server ships nothing; `BestiaryGui` shows all twenty rows on one grid behind `Config.Enemies.BestiaryEnabled`, which ships false. PetGui's shelf and hatch reveal go through the same `of` with a `PetModelGenerator` rig, which is the one place the two generator families meet and they meet only at a camera.

`EnemyWard` is the one file on this side that knows pets exist, and it knows one thing: whether a position is inside a running ward. (`EnemyCombat` reads a `PetArmor` attribute, which is not the same thing: an attribute with a number on it is not knowledge of who wrote it.) PetService writes `WardRadius` on a follower rig while its ward is up, which is the same flag-on-an-instance channel the Ghost powerup and the Cloak ability already use, and the controller turns a covered position into the Return branch. The gate sits after `behavior.update` rather than with the freeze and stun gates above it, and that placement is load-bearing twice: a claimed tick is a move the player was already shown, so a telegraphed charge still lands where it said it would, and a Burrower under the floor is anchored, so a ward that held it mid-travel would hold it there forever.

Four modules are shared by more than one type and are the reason the behaviors are small. `EnemyCombat` owns everything that takes a player's health, which is now a swing, a slow, a shove, a bolt in flight, a snare on the floor and a shockwave, plus the runtime instances the last three leave: they are filed under the controller that made them and `clearRuntime` destroys the lot from `stop`. All six land through `applyDamage`, which is why a pet's `PetArmor` is subtracted there and at no call site; it reads a replicated player attribute and never `PetInventory`, so this module still does not know what gear is, and the fraction is already capped by the resolver that published it. `EnemyAlert` is one enemy telling the others where you are, and it is filtered by floor band always and by building for the types whose alarm should stay indoors. `EnemySpawner` is the one way an enemy comes to life and, since E6, the one default way one stops being live, so a Splitter's children and a debug spawn are made and unmade the same way `EnemyService` does it. And a behavior that wants to be faster or slower names a multiplier on the controller rather than writing `WalkSpeed`, so `EnemyFactory`'s clamp still holds and nothing outruns the player without having shown them a line to sidestep first.

Fields on a row that nothing reads yet are listed in `EnemyDefinitions`' own header, and that list is worth keeping honest, because a number nobody reads looks exactly like a number that is not working.

## Abilities

The stall sells two kinds of thing. An **upgrade** is a number that is always true (Fast Feet, Coin Magnet). An **ability** is a verb on a key, and a player who owns three can only be using one at a time, so it has something an upgrade does not: a selection, changeable anywhere and at any point. `src/server/Abilities/` is the abilities; `AbilityService` is everything they share. Sprint is deliberately neither: it is free, permanent and on its own key, so it never competes for the selection.

Both kinds are rows in `Config.Shop.Upgrades` and **`Mode` is the whole test** (`Config.abilityDef`). One table because a tier is a tier and the keys cannot collide, which is also why ability tiers live in the profile's existing `upgrades` map: splitting them would have retired the Wall Walker tiers players had already bought for the sake of a tidier field. The only new profile field is `selectedAbility`.

**One charge, not one meter each,** and the rest of the design falls out of it. The charge is a fraction from 0 to 1 refilled at every `LevelTrigger`; a `Hold` drains `1/SecondsPerTier[tier]` a second and a `Cast` takes `ChargeCostPerTier[tier]` in one go. So owning three abilities is three ways to spend one floor rather than three floors of resource, switching on an empty bar buys nothing, and a tier makes its ability cheaper rather than issuing a second meter. It is also one bar to read instead of three.

**The service owns everything shared; a module owns only what it does.** The charge, the selection, the refill, the grace, the remotes and the teardown on death are all in `AbilityService`, which is why `Abilities/Cloak` is thirty lines. Same split as `EnemyController` and a `Behavior`, for the same reason. Hooks are `start`, `stop`, `blocked` and `cast`; `BaseAbility.extend` errors at require time on anything else.

Two things are worth knowing before touching it. `blocked` is the whole reason a phase can outlive an empty charge: going solid inside a wall is how a player gets stuck, so the service holds the ability running while its module says stopping is unsafe, capped by `Config.Abilities.GraceSeconds` because a grid maze's walls all meet at the corners. And ownership reaches the client as replicated player attributes (`AbilityTier_<Key>`, `SelectedAbility`) rather than over the remote, so the HUD is correct on its first frame with nothing to request.

**Adding an ability is one `Config.Shop.Upgrades` row, one key in `Config.Abilities.Order`, and one module under `Abilities/` named for that key.** No service is edited: the shop grows a pedestal, the HUD grows a button and a number key, and the profile needs no migration. Unlike an enemy, a key with no module is dropped from the roster with a warning rather than given the base class, because a baseline enemy still chases where a baseline ability is a pedestal charging coins for a key that does nothing. The pedestal is generated from the same list and is *not* dropped with it, so that case is still for sale until the warning is read.

## Server-to-server events

Services talk to clients over RemoteEvents and, since the pet system, to each other over BindableEvents in `ServerScriptService`. Same shape either way: one table argument discriminated by a `kind` field.

The difference is who creates it. A RemoteEvent is created by its owning service and waited on by the client. A BindableEvent is created **FindFirstChild-or-create on both ends**, because scripts in `ServerScriptService` start in arbitrary order and a listener that happened to run first would wait forever on something it is allowed to make itself.

- **`MazeProgress`**, fired by TowerTimerService from `enterFloor` and `completeTower`. Both kinds fire unconditionally, so which of them counts as "a maze" is a config read on the listening side rather than a decision baked into the timer. Firing from `completeTower` after `state[player] = nil` is what stops a tower being handed to a listener twice, poll and touch both reaching the same place.
- **`PetsChanged`**, fired by any service that mutates a profile's pets or eggs. PetService listens and re-pushes the projection and re-rigs the followers, which is how IncubatorService and DailyRewardService reach the client without owning a remote.
- **`UpgradesChanged`**, fired by PurchaseService when a Robux receipt lands an upgrade tier. SaveService listens and answers with `applyStats`, which is how the bought tier reaches the character without SaveService learning what a receipt is.
- **`PromptPurchase`** is the one BindableFunction beside them, created by PurchaseService alone since a function has a single owner: a storefront service validates its own context and asks it to open the Robux prompt, and it refuses everything a receipt could not spend.

All gameplay tuning lives in `MazeConfig`. World-shape knobs meant to change between playtests (seed, levels, pregenerate count, lamp brightness, moving wall start level, phantom count) live in `Config.World`; structural geometry constants (cell size, wall height, plot grid) live in `MazeGenerator.CFG` because changing them invalidates the whole city. Do not scatter magic numbers into services.

One list in `MazeConfig` is not only tuning and is worth knowing about: `Config.Shop.Order` plus `Config.Abilities.Order` decide how many pedestals the stall has, and `buildShop` sizes the counter from the total. That is the only place a config edit changes geometry, and it changes it by construction rather than by a draw, so the delta stays countable (five instances per pedestal per building, thirty per section).

Content is the one thing that does not live in `MazeConfig`. A catalogue grows by entries where tuning grows by edits, so pets and eggs are `ReplicatedStorage.PetCatalog` and `ReplicatedStorage.EggCatalog` while the numbers governing the system as a whole (`HatchUnit`, storage caps, XP rates, follow distance, prompt distance) are `Config.Pets`. `Config.Pets.HatchUnit` is the one to be careful with: it silently rescales every `mazesRequired` in `EggCatalog`, so flipping it is a catalogue pass, not a knob turn.

## Conventions

- Tabs for indentation.
- No comments that restate the code. Comments explain why, or document a non-obvious invariant.
- Keep files compatible with `luac -p` where it costs nothing (avoid `+=`, `continue` unless there is a reason); it enables syntax checking outside Studio and in CI.
- Attribute names, tag names, and config keys are PascalCase.
- Direct file edits over generation scripts. When modifying these files, edit them in place rather than writing scripts that rewrite them.
- No em dashes in any file in this repo.

## Known gaps and deliberate deferrals

- **Slide physics.** SECTION_GAP of 620 makes the natural slope about 16 degrees, too shallow for gravity alone, hence the boosters. Shortening the gap below about 400 allows removing them.
- **Part count.** Roughly 8k parts per section, windows being the biggest single contributor. First optimization if needed: merge collinear maze wall runs, at the cost of complicating per-cell wall tagging. Also consider `workspace.StreamingEnabled` before any geometry surgery; with lazy generation plus streaming, section count is effectively unbounded. Do not optimize preemptively.
- **Enemy pathfinding scale.** Bounded by proximity rather than by section count: live rigs are only those near a player, so cost tracks players and not city size, and `Config.Enemies.GlobalCap` is the ceiling over that. The remaining flat cost is one sweep over every marker twice a second, about 1800 magnitude tests a second at five sections and four players, plus a sort of whatever is in range. If section count ever grows far enough for that to matter, bucket the markers spatially in the scan loop; do not put the cost back into keeping rigs alive.
- **Enemies cannot be damaged.** There is no combat, so a row's `health` and `Config.Enemies.HealthPerLevel` set a MaxHealth nothing reads and the `Died` path is reachable only in principle. It is wired correctly anyway (despawn, then respawn after `Config.Enemies.RespawnSeconds`, or the spawner's default linger-and-destroy for a rig no marker placed), so adding a weapon is a weapon and not also a lifecycle. `EnemyController:takeDamage` is the entry point when one arrives. Two E4 types wait on it and are otherwise finished: the Splitter, whose split is on death, and the Warden's enrage, which is a health threshold nothing crosses.
- **Footprint variety.** All buildings share one footprint; styles vary skin, windows, crown. True silhouette variety requires per-building maze dimensions, which touches slab math, facade math, and slide targeting. Treat as a feature, not a tweak.
- **Progress within a run is not saved.** SaveService persists coins, upgrade tiers, and furthest section reached, but a rejoining player always spawns at section 1: `furthestSection` is stored without yet being spent. A checkpoint spawn reading it against existing `TowerStart` tags is the natural next feature, and needs no data migration.
- **Generated world is not inspectable in edit mode.** Cost of dropping the plugin. If you need to eyeball geometry without playing, add a temporary `RunService:IsStudio()` branch in a throwaway script, or run the game and use the server-side explorer during Play.

## Pet & Egg System

Active work on the pet/egg system follows [docs/PETS_PLAN.md](docs/PETS_PLAN.md) (clutch-based work units, prerequisites audit, exit criteria) and [docs/PET_EGG_DATA_SPEC.md](docs/PET_EGG_DATA_SPEC.md) (types, config shape, server-side state transitions). Read both before touching pet, egg, incubator, or daily reward code. If something needed isn't in the plan, update the plan first rather than inventing a parallel system.

The spec was written against a generic Roblox project, so its paths are not this repo's paths and some of its shape collides with decisions already made here: coins live in `leaderstats` and are stored exactly once, the wipe is `Config.Persistence.KeyPrefix` rather than the in-payload `schemaVersion`, and there is no ProfileService. The plan's "Repo reconciliation" section is the authority on every one of those; the spec is the authority on the data model itself. `docs/` is outside the three `src/` folders Rojo maps, so nothing here reaches the place file.

How a pet *looks and moves* is a second plan, [docs/PET_LOOKS_PLAN.md](docs/PET_LOOKS_PLAN.md), in Sets rather than Clutches, and all four are done: the generator and the recipes, the follower wearing them, the portraits, and the motion. Its invariants are the ones to read before touching `PetModelGenerator`, `PetRigDriver` or `sterilise`, and two of them are cheap to break by accident: `build` is pure so a client can run it, and the driver writes `Motor6D.Transform` and never C0, C0 being the baseline `rigOf` measures from. `tools/petlooks/check.sh` builds every rig and runs a minute of motion over it under the luau CLI, outside Roblox, in milliseconds; run it after any recipe or driver edit.

What a pet *wears* is a third plan, [docs/PET_ACCESSORIES_PLAN.md](docs/PET_ACCESSORIES_PLAN.md), also in Sets, and all five are done: the data layer and the resolver, wearing and rendering, the effects that are one addend each, the economy plus the two award-site effects, and the two client clarity draws. Sets 3 and 5 are the ones that reach out of the pet system, so their invariants are the ones to hold: **gear on a benched pet does nothing**, resolved for equipped pets only in `PetInventory.wornEffects` and capped there so no consumer clamps; **one attribute, one writer, readers add**, which is how a Coin Chain reaches the magnet without SaveService ever hearing about it; and **no consumer reads `AccessoryCatalog`**, services taking the totals table or the attribute published from it. PetGui is the one file that reads the catalogue and is not a counterexample: a shop has to name items nobody owns, and it resolves no effect. Set 5 shipped in the order the plan inverted, source before effects, because until a player could buy anything every earlier Set was unreachable code, and Set 4 followed it and took the attribute table from six rows to eight. What is left of the plan is its three open decisions, of which `Armor` is the one a playtest settles.

What the world *means* is a fourth plan, [docs/LORE.MD](docs/LORE.MD), and it carries one rule the rest of the repo has to know: **all player-facing lore text lives in LORE.MD first, then in `Lore.lua` and `Journal.lua`.** No lore line is invented at a keyboard; new content is a doc edit in the same branch, and a line changed in one place is changed in both or in neither. Both configs check themselves at require time, one way only: every key must resolve to a real catalogue id, while an id with no lore is legal and simply has no flavour text. That turns a typo from a Codex row that silently never appears into a startup error, and it is why adding a pet or an enemy never breaks the lore layer while renaming one does, loudly. Clutch 7 in PETS_PLAN.md is the work; units 1 and 2 are done, which is the two configs and the profile's `codex` table.

Clutches 1 through 6 are done: data layer, incubator and hatching, follower and Glow, XP and dailies, the UI, and Ward. The plan records what was decided along the way, including the three things it did not originally cover (a profile module, an egg storefront at the roost, and pet release still not existing). Clutch 6 is the one to read before touching either system: it is the first pet ability that reaches into another, and the settled decision explains why a defensive pet wards rather than fights, and why it is a duty cycle rather than an aura.

## Robux

What things cost in real money is [docs/ROBUX_PLAN.md](docs/ROBUX_PLAN.md), in Registers. R1 (the derived ladder, `Storefront`, the `tools/robux/` dashboard worklist), R2 (the receipt spine in `PurchaseService`, the profile's `receipts` table, the Studio `/buy` command), R3 (the roost's two Robux intents and the second price on PetGui's shop rows) and R4 (the stall's `RobuxPrompt`, one per pedestal, bound by SaveService through the prompt gate) are built; R5 (direct pet sale) is not, and no `robuxProductId` is set until the dashboard products exist, absent meaning not for sale. It is listed here rather than under the pet system because it reaches the stall as well as the roost. Two rules are worth knowing before any of it is written: a **Robux price is derived from the coin price** by one pure function in `Storefront`, so the ladder the game already tuned against effectiveness is the only ladder either currency reads and a rebalance moves both; and **`coinCost` and `robuxProductId` are two independent one-field rules**, absent meaning not for sale in that currency, which is how the streak Legendary and the event trail stay off one shelf without a second flag. The receipt spine inherits `PlayerProfiles`' failure posture and sharpens it: a profile that failed to load refuses every purchase, because a grant into one is money taken for something that vanishes at the next join.

## What "done" looks like for a change

1. `selene src/` clean.
2. Generator changes: run twice with the same seed and confirm identical output (part counts per section folder are a cheap proxy; `print(#folder:GetDescendants())`).
3. Runtime changes: Play test one full floor including a score award, one death and floor respawn, one moving wall cycle on level 5+, and one slide ride into a lazily generated section.
4. Profile changes: rejoin and confirm the field came back, then confirm a Studio session with no DataStore API access still plays and still saves nothing. The second half is the one that gets skipped and it is the one that protects everyone's coins.
5. No new magic numbers outside `MazeConfig`, `Config.Pets` or `MazeGenerator.CFG`.
